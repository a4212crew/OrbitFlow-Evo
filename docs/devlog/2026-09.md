### 2026-09-20 — Device capability and future OSS architecture

**Objective**
- Define OrbitFlow's long-term architecture so reusable network-equipment functions can support both internal automation workflows and future external REST/OSS consumers.

**Prompt / Request**
- Separate reusable device operations from higher-level features, normalize device state into structured outputs, support deterministic analysis/remediation/troubleshooting workflows, and ensure the same capabilities can later be exposed through REST APIs as an OSS layer.

**Files changed**
- `AGENTS.md`
- `CURRENT_STATE.md`
- `docs/architecture/device-capability-oss-model.md`
- `docs/devlog/2026-09.md`

**Architecture / Decisions**
- OrbitFlow will evolve around reusable device capabilities rather than one-off workflow scripts.
- Vendor-specific commands and parsers remain isolated behind common capability-oriented interfaces.
- Higher-level features compose normalized device capabilities for audit, troubleshooting, provisioning, remediation, service assurance, and other operational tasks.
- Observation, analysis, planning, configuration application, verification, and recording remain separable.
- Future REST APIs, GUIs, schedulers, and OSS/BSS integrations must call the same internal application/capability interfaces instead of duplicating device logic.
- Normalized structured models should be reusable by workflows, reports, JSON/API responses, and future integrations.
- Raw vendor CLI should not become the primary external OSS abstraction.

**Validation / Tests**
- Documentation/architecture change only; no runtime behaviour changed.

**Known issues / Limitations**
- Exact Python interfaces, model classes, API framework, and endpoint schemas are intentionally deferred until capabilities are implemented incrementally.

**Next step**
- Use the interface-description collector as the first implementation that follows the reusable capability -> normalized model -> workflow/reporting pattern.
